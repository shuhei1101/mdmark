## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 共有するブラウザ | `storybook-setup.ts` が Storybook の起動の後に子プロセス `tests/integration/browser-server.ts` を起動する。子プロセスは `chromium.launchServer()` で Chromium を 1 つ起動して温め、`wsEndpoint` を標準出力へ出す。`storybook-setup.ts` はそれを `provide` で各ファイルへ指定し、`globalSetup` の終わりに子プロセスへ SIGTERM を送ってブラウザを閉じさせる | `globalSetup` の中で Playwright を呼ぶと、Playwright が API を呼ぶたびに取るスタックトレースを vite 8.3.6 の module runner が読めず（`globalSetup` のモジュールのコードを文字列でなく Buffer で持ち、`extractInlineSourceMap` が `code.charCodeAt is not a function` で失敗する）、`npm run test:integration` が起動時に止まるため、子プロセスにする |
| ファイルごとの準備 | `createBrowserHolder` の `launch` は起動と温めをせず、共有するブラウザにつなぐだけにする。`close` は接続だけを切る | - |
| ページを閉じる | `openStory` で開いたページを、テストの終わり（`onTestFinished`）に閉じる | テストの中で閉じたページ（`card-grid.story.test.ts`）は二重に閉じても失敗しないようにする |
| 待ちの上限 | 温めの待ちの上限 `WARM_UP_TIMEOUT_MS` を子プロセスで使用する。Chromium の起動の上限 `LAUNCH_TIMEOUT_MS`・接続の上限 `CONNECT_TIMEOUT_MS` は外側の作業の上限から導き、子プロセスが接続先を出すまで待つ上限は、起動・接続・温めの待ちの合計に 50% の余裕を足す。`integration-storybook` の `hookTimeout` は、各ファイルの `beforeAll` が接続だけになるため、規約『資源の値の決め方』で導き直す | - |
| 並列の上限 | `integration-node`・`integration-storybook`・`integration-browser` の `maxWorkers` を、`os.availableParallelism()` の半分（1 以上）にする。Vitest 5.0.4 は同じ `sequence.groupOrder` のプロジェクトを 1 つのグループにまとめ、グループの `maxWorkers` を、Node のプール（`integration-node`・`integration-storybook`）とブラウザのプール（`integration-browser`）のそれぞれの上限に使う（`maxWorkers` が違うプロジェクトを同じ `groupOrder` に置くと起動時にエラーにする）ため、3 つに同じ値を置く。`unit`・`unit-browser` と同時に選んでもエラーにしないよう、3 つの `sequence.groupOrder` を `1` にする | 2 つのプロジェクトだけに置くと、`npm run test:integration` が起動時に `Projects "integration-browser (chromium)" and "integration-node" have different 'maxWorkers' but same 'sequence.groupOrder'.` で止まることを確かめた |
| 測定 | 同じ端末で、修正の前（develop）を引数なしと `--maxWorkers=4` の 2 回、修正の後を引数なしで 1 回 `npm run test:integration` を実行し、所要時間（vitest の Duration）と、実行中のメモリの使用の最大（テストのプロセスと Chromium の PSS（`/proc/{pid}/smaps_rollup` の `Pss`）の合計を 1 秒ごとに測った最大）を記録する | ほかの全件の実行と重ならない状態で測る。RSS の合計は Chromium のプロセス間で共有するページを重ねて数え、プロセスの数を変える修正の前と後を比べられないため、PSS で測る |
| テスト実行方法 | 結合テスト（フロント）の説明の各ファイルの `beforeAll` の待ちの記載を、プロジェクトで 1 回の温めに修正し、並列の上限を記載する | - |

### 待ちの上限の導出

待つ相手はテストが自分で起動した Chromium と、そのページを閉じる処理で、規約『資源の値の決め方』の「自分の処理の完了を待つだけのタイムアウト」に当たる。役目はハングの検知だけのため、外側の作業の上限から導く。

| 値 | 導き方 | 参考の実測（ほかの全件の実行が無いとき） |
| --- | --- | --- |
| `integration-storybook` の `hookTimeout` = 60 秒 | 外側の作業の上限の `testTimeout`（60 秒）と同じ。`beforeAll` の接続・`afterAll` の切断・`onTestFinished` のページを閉じる処理に効く | ページを閉じる 489 回の p99.9 は 29ms |
| `CONNECT_TIMEOUT_MS` = 30 秒 | 外側の `hookTimeout` 60 秒の内側に収め、残りを余裕にする | 接続 62 回の p99.9 は 33ms |
| `LAUNCH_TIMEOUT_MS` = 30 秒 | 接続と同じ値 | 起動 12 回の最大は 46ms |
| 子プロセスが接続先を出すまでの上限 | 入れ子の待ち。起動・接続・温めのストーリーごとの読み込みと描画の待ちの合計 + その 50% | - |
