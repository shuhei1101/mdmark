# 要件

## 要望

knowledge の規約『ドキュメント管理』の `## 関連`（[shuhei1101/knowledge#42](https://github.com/shuhei1101/knowledge/issues/42) で入った `docs/rule/dev-document-management.yaml` の `related-01`〜`related-05` と、`schemas/common.schema.yaml` の `related_item`）に、索引の `docs[].related` を合わせる。

### 関連の要素

- `docs[].related` の要素は、`to`（相手の文書の `id`）・`type`（関係の種類）・`when`（いつ読むか、1 文）を必須で、`paths`（関連が当たるファイルの glob の並び）を任意で持つオブジェクトにする
- `type` は `requires`・`references`・`replaces`・`part_of`・`change_together` のどれか
- `when` は空にできない
- `docs[].related` の件数に上限を置く

`未確定`: 件数の上限（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | knowledge の `schemas/common.schema.yaml` の `related` と同じ 8 件 | knowledge の索引と同じ上限で、knowledge の文書をそのまま索引に載せられる | 8 件を超える今の文字列の `related` は Schema に合わなくなる |
| B | 上限を置かず、点検だけが上限を超えた関連を知らせる | 今の索引が Schema に合わなくならない | 規約の「件数の上限は種類のスキーマで決める」を Schema で表せない |

推奨: A

規約が上限を種類のスキーマで持つと定めており、mdmark の索引の文書は 1 つの種類のため。
案 A は関連が 9 件以上ある公開済みの索引を Schema に合わなくする（公開済みインターフェースの互換性破壊）ため、インターフェース定義設計で規約『確認事項の投稿』に沿ってユーザーへ回す。
9 件以上ある索引の移し方（移行の手順で件数を減らせないとき、`mdmark upgrade` が止まって知らせるか）も、同じ確認事項に入れる。

### 文字列の要素

- 今の文字列の要素も読めるままにし、`type` と `when` を持たない関連として扱う
- 点検が、文字列の要素をオブジェクトへの書き換えを求めるずれとして知らせる

### 逆向きの関連

- 関連は片側だけに記載し、逆向きはツールが出す（規約の `related-03`）
- MCP の `find_docs` の `related_to` で引いた各文書に、関係の種類・向き（相手から自分か、自分から相手か）・`when` を添える
- 逆向きの関係の名前（`requires` の逆など）は英語の識別子でインターフェース定義設計で決める
- 描いた文書の末尾の関連文書の一覧と被参照の数は、今と同じく `related` の相手から数える（要素の `to` を相手として読む）

### change_together の点検

- `change_together` は両側に記載する（規約の `related-03`）
- `checkIndex`（`mdmark check` と MCP の `check`）は、片側にしか記載していない `change_together` をずれとして知らせる
- `change_together` の組のうち片方の文書だけが変わったことを、直し忘れとして知らせる
- 直し忘れは、`mdmark check` と MCP の `check` に任意で渡す比べる基準の git の ref（例 `origin/develop`）から検査する。渡さないときは検査しない
- 変わったファイルは、基準と HEAD の merge-base から作業ツリーまでを比べて引く
- 基準を引けないときは、引けないことと直し方を出して 0 以外で終わる

### その他の点検

- `to` が索引の文書に無い関連は、今の `broken_ref` で知らせる。`mdmark check` はずれがあると終了コード 1 で終わり、CI を止める（規約の `related-05`）
- 本文でリンクしている文書を `related` にも記載したら、ずれとして知らせる（規約の `related-04` の「本文でリンクしている相手は重ねない」）
- ずれの種類の名前は英語の識別子でインターフェース定義設計で決める

### update_index

- MCP の `update_index` の `kind: doc` で、`related` をオブジェクトの並びで書ける
- 書く前の索引のスキーマの検査は今と同じく当て、`to`・`type`・`when` の欠けと、知らない `type` を拒む

### 移行の手順

- 索引の Schema を変えるので、`migrations/next/` に移行の手順か、`migrations/no-steps.yaml` に行を置く（CLAUDE.md の `## 設定・索引の Schema`）。文字列の要素は読めるままにするので、件数の上限の決着で移行の手順が要らなければ `migrations/no-steps.yaml` の行で足りる

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| `paths` の glob に当たるファイルのパスを渡して、関連する文書を引く | Issue は `paths` を持たせることまでを求め、引き方を求めていない | 予定なし |
| 補足だけの文書の逆向きの関連を出さないマーカー（DITA の `targetonly` 相当） | R-26 の調査担当の提案で、knowledge の規約『ドキュメント管理』に入っていない | 予定なし |
| `deprecated` の相手への関連を推薦から外す | R-26 の調査担当の提案で、knowledge の規約に入っていない。mdmark の索引は文書の状態を持たない | 予定なし |
| 関連の相手にコード・ルールを指す種類（D-25 の `doc` / `code` / `rule`） | knowledge の規約『ドキュメント管理』は `to` を相手の文書の ID と定め、コードは `code_refs` に分けた | 予定なし |
