# 要件

## 要望

ビルドを丸ごと流すテストの待つ上限を、実測の所要時間から規約『資源の値の決め方』の「下流を待つタイムアウト」（実測の p99.9 + その 50% の余裕）で導いた値にする。
確かめる内容（準備・実行・検証）は変えない。

| 対象 | 変えるもの |
| --- | --- |
| 結合テスト `tests/integration/lib/build.test.ts` | `BUILD_TIMEOUT_MS`（今は 120 秒）。この定数を使う全てのテストに効く |
| 単体テスト `tests/unit/scripts/build.test.ts` | `createBuildRoot` の後に `main` でビルドを丸ごと流すテストへ、ファイルの定数で個別の `timeout` を持たせる。`vitest.config.ts` の `unit` プロジェクトの `testTimeout: 30_000` は変えない |

- 実測: WSL2 の `/mnt/c` の作業ツリーで、対象のファイルだけの実行を 5 回と、そのファイルを含む全件実行（結合は `integration-node`、単体は `npm run test:unit`）を 3 回流し、対象のテストの所要時間の最大値を p99.9 として使う
- 値: 最大値 × 1.5 を 10 秒単位で切り上げる。定数の横のコメントに、実測の最大値と導き方を書く
- 終わりの条件: 値を変えた後の全件実行を結合・単体それぞれ 3 回流し、対象のテストがタイムアウトで fail しない

## 変更箇所の由来

| 対象箇所 | commit | 目的 | 変更回数 | 影響 |
| --- | --- | --- | --- | --- |
| `tests/integration/lib/build.test.ts` の `BUILD_TIMEOUT_MS` | [a6e0aad8](https://github.com/shuhei1101/mdmark/commit/a6e0aad8e7f166a86f157761f802b77169e08e0b)（`HTML コメントの印で表・注意書き・タブなどの表示を付ける拡張記法を作る (#19)`） | 120 秒を置いた。コメントは「ビルド（型定義を書く `tsc` を含む）を子プロセスで流すテストの待つ上限」で、PR #19 の PR ドキュメントとレビューのやり取りに値の根拠（実測）の記載は無い | 1 回 | 後から [PR #86](https://github.com/shuhei1101/mdmark/pull/86) が足した `test_normal_when_api_checked_before_use` などもこの定数を使う。実測から値を導き直す直し方は、ビルドを子プロセスで流す時間を待つ目的を壊さない |
| `vitest.config.ts` の `unit` プロジェクトの `testTimeout` | [d2e71837](https://github.com/shuhei1101/mdmark/commit/d2e71837f2e865901d66e291c4b58fb2139d8835)（`サーバー無しで Markdown を 1 枚で完結する HTML に書き出し、複数の文書を 1 枚にまとめる CLI を作る (#32)`） | 30 秒を置いた。全件を並列に流すと最初の import が CLI のビルドの負荷に重なり、既定の 5 秒を超えて既存のテストが落ちるのを避けるため（[PR #32](https://github.com/shuhei1101/mdmark/pull/32) の implementer の報告） | 1 回 | 単体の全テストに効く既定の上限で、ビルドを丸ごと流すテストの時間を見込んだ値ではない。この値は変えず、ビルドを流すテストだけに個別の上限を持たせる |

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| テストの所要時間の短縮（ビルドの `tsc` を省く・作業ツリーの準備を共有する 等） | 確かめる内容が変わる。待つ上限を実測から導けば、全件実行で fail しない要望を満たせる | 予定なし |
| `tests/integration/lib/upgrade.test.ts` の `BUILD_TIMEOUT_MS`（180 秒） | タイムアウトの報告が無い | 予定なし |
