## 変更方針

<!-- table: data -->

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| コマンド | `main` に `upgrade` を足し、`--plan`・`--yes` を受ける。目標の版はビルドが呼んだ CLI に埋めた版（`version()` と同じ出所）にする | 呼び方は既存のコマンドと同じ `npx github:shuhei1101/mdmark#v{目標の版} upgrade`。目標の版を引数で受けると、呼んだ CLI の版の形で点検して正しい設定を戻すため受けない |
| 設定の形の正 | `theme`・`extensions`・`build`・`version` を `schemas/mdmark.config.schema.json` に足し、設定の設計書の lead と Schema の `description` を「ライブラリ本体と CLI が読むキー」に直す | `validateConfig` の検めは Schema と同じ形のまま |
| 手元の版 | 設定に `version` を足し、`init` が置く設定に呼んだ CLI の版を書く。`version` が無い設定は利用者に手元の版を聞く | 単一ユースケース設計で案 A に決めた |
| 移行の手順の形 | `migrations/{版}/steps.yaml` を手順の並びとし、手順ごとに種類（`rename_key`・`set_default`・`map_values`・`replace_mark`・`call`）・対象・引数・壊す印を持つ。`steps.yaml` の形は `schemas/mdmark.steps.schema.json` で縛り、CLI が読むときと配布物のビルドで検める | `call` のスクリプトは同じ版のフォルダに置く。出していない版の手順は `migrations/next/` に置く。形は ER 図『移行の手順』 |
| 当て直し | 宣言の手順は、既に当たった後の状態に当てても同じ結果にする（`rename_key` は新しい名前のキーが既にあれば何もしない 等）。手順の種類ごとの扱いはインターフェース定義『版を上げる』の `当て直し` の制約 | Ctrl-C などで写しから戻せずに止まっても、次の `upgrade` が当て直せる |
| 手順の対象 | 設定・索引のキーは設定ファイルと、設定の `index` が指す索引を対象にする。文書の印の書き換えは、手順に書いた glob に当たる文書を対象にする | YAML の書き換えは採用済みの yaml で、コメントと並びを残す |
| 当てる順 | 手元の版より新しく目標の版以下の版を、版の比較（`{MAJOR}.{MINOR}.{PATCH}`）の昇順に当てる。版のフォルダが無い版は手順なしとして飛ばす | - |
| 写しと戻し | 当てる前に、手順が書き換えうる全てのファイルを写しのフォルダへ写し、途中で失敗したら写しから戻す。成功したときも写しを残し、場所を出す | 写しのフォルダの場所は設定ファイルのあるフォルダの下にし、中身が `*` だけの `.gitignore` を置く |
| 点検と版の書き換え | 全ての手順を当てた後に `runCheck` と同じ点検を流し、ずれが 0 件のときだけ手元の版を目標の版に書き換える。ずれがあれば写しから戻す | `set_default` の値を聞く指定は、手順を当てる前に聞いておく |
| 変更履歴 | 呼んだ版のパッケージに入った `docs/はじめに/変更履歴.md` の表から、当てた範囲の版の行を出す | 変更履歴の表の形は 1 PR = 1 行のまま変えない |
| 開発側の点検 | `npm run build` が、`schemas/` の JSON Schema を最新の版のタグから変えたのに移行の手順も `no-steps.yaml` の行も無ければ、配布物を書かずに止める。見る手順は、`version.ini` が最新の版のタグと同じなら `migrations/next/`、新しければ（release のビルド）`migrations/v{版}/` で、release のビルドで `migrations/next/` が残っていれば止める。版のタグが無ければ飛ばす | 単一ユースケース設計で案 A に決めた。release で `next/` を `v{版}/` へ移す段は開発コマンドに書く。比べる版は、`--version` で渡した版（hotfix のビルド）があればその版、無ければ `version.ini` の版にする（[レビュー](https://github.com/shuhei1101/mdmark/pull/39#discussion_r4301564687)） |
| 対応テストファイル | テストを作る段で、作ったファイルを設計書に書く。E2E は `tests/e2e/単一ユースケース/版を上げる.spec.ts` をシナリオ『版を上げる』の `test_file` に、結合はインターフェース定義『版を上げる』の `test_file` に、単体は `tests/unit/src/cli/{versions,migrations,backup,changelog,prompt,upgrade}.test.ts` と `tests/unit/scripts/migrations.test.ts` をモジュール構成『版を上げる』『ビルド』の `test_files` に書く | 書くツールは無いテストファイルを指す `test_file` を受け付けない |
| エラー返却 | 既存のコマンドと同じく `CliError` で原因と直し方の 1 文を出して終了コード 1 にする | - |
| 既存機能への影響 | `check`・`export`・`build` は手元の版のキーを知らないキーとして扱わず、設定の形の検めに足す | Schema の最上位は知らないキーを拒まないまま |
