# 要件

## 要望

mdmark の版が上がったとき、使う側が `mdmark upgrade` で手元の版から目標の版までの移行の手順を版の順に当て、その範囲の変更履歴を見られる。
開発側は、設定・索引のスキーマを変えた版に移行の手順を置き忘れたまま配れない。

<!-- table: data -->

| 項目 | 要件 |
| --- | --- |
| コマンド | `mdmark upgrade [--plan] [--yes]` を足す。目標の版は、呼んだ CLI の版（`npx github:shuhei1101/mdmark#v{目標の版} upgrade` のタグ）にする |
| 手元の版 | 設定ファイルの `version`（`v{MAJOR}.{MINOR}.{PATCH}`）を手元の版とし、`init` が置く設定に呼んだ CLI の版を書く。`version` が無い設定は、利用者に手元の版を聞く。手元の版が目標の版より新しいときは何も当てず、原因と直し方の 1 文を出して終了コードを 0 以外にする。同じ版のときは何も当てずに終了コード 0 で終える |
| 移行の手順 | 版ごとに `migrations/{版}/steps.yaml` を置き、手元の版より新しく目標の版以下の版の手順を、版の順に当てる。手順の種類は、設定・索引のキーの名前を変える・キーを足す（値を利用者に聞く指定を持てる）・値を読み替える・文書の印を書き換える・宣言で書けない移行をスクリプトで当てる、の 5 つ。どの手順も、当て直しても同じ結果になる（新しい名前のキーが既にあればキーの名前を変えない 等）。スクリプトの手順も当て直せるように書く |
| 当てる前に示す | `--plan` は何も書き換えず、当てる版ごとの手順・その範囲の変更履歴の行・壊す手順の有無を出す |
| 壊す手順 | 手順に壊す印（`destructive`）があるとき、`--yes` が無ければ当てる前に確かめ、断られたら何も書き換えずに終える |
| 失敗したとき | 当てる前に書き換える対象の写しを取り、手順の途中で失敗したら写しから戻し、失敗した版・手順・理由を出して終了コードを 0 以外にする |
| 成功したとき | 全ての手順を当てた後に `mdmark check` と同じ点検を通し、通ったときだけ設定の版を目標の版に書き換え、写しの場所を出す。点検が通らなければ写しから戻して版を書き換えず、ずれの一覧を出して終了コードを 0 以外にする。途中で止まっても、次の `upgrade` が同じ手元の版から当て直す |
| 変更履歴 | 当てた範囲（手元の版より新しく目標の版以下）の変更履歴の行を出す |
| 設定の形の正 | 設定の形の正を `schemas/mdmark.config.schema.json` にし、今はコードだけが検めている `theme`・`extensions`・`build` と、新しい `version` を Schema に足す |
| 開発側の点検 | 配布物のビルド（`npm run build`）が、設定・索引の JSON Schema（`schemas/`）を最新の版のタグから変えたのに移行の手順が無いとき、配布物を書かずに失敗する。出していない版の手順は `migrations/next/` に置き、release で `version.ini` を上げる commit で `migrations/v{版}/` へ移す。`version.ini` が最新の版のタグより新しいビルド（release のビルド）は `migrations/v{版}/` を見て、`migrations/next/` が残っていれば失敗する。版のタグが 1 つも無ければ点検を飛ばす。広げるだけの変更は、理由と変えた後の Schema の SHA-256 を書いた一覧（`no-steps.yaml`）に載せて通す |
| 誤りの扱い | 設定ファイルが無い・読めない、手元の版が版の形でない、手順のファイルが読めない・形に合わないときは、何も書き換えず、原因と直し方の 1 文を出して終了コードを 0 以外にする |
| 完了の基準 | 手順を持つ版を 2 つ以上またぐ見本の設定・索引・文書で `upgrade --plan` と `upgrade` を流し、手順が版の順に当たって点検が通り、設定の版が目標の版になる。手順の途中で失敗させると、書き換えた全てのファイルが当てる前の中身に戻る |

<!-- /table -->

手元の版を持たない設定（v0.3.0 までの `init` が置いた設定）の扱いは、単一ユースケース設計で案 A（設定に `version` を足し、無ければ利用者に聞く）にした。
当てる手順は手元の版で決まり、取り違えると移行が設定を壊すため、分からないときは聞く。

開発側の点検を流す場所は、単一ユースケース設計で案 A（配布物のビルドの検査に足す）にした。
GitHub Actions などの CI は無く、配る前に必ず通るビルドに置けば止め忘れが無い。
`version.ini` は release の commit でだけ上がるため、出していない版の手順は `migrations/next/` に置く（[レビュー](https://github.com/shuhei1101/mdmark/pull/39#discussion_r4301535091)）。

## スコープ外

<!-- table: data -->

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 使う側のページに書いた配布物の URL のタグの書き換え | 判断: 含めない。タグは使う側のサーバーのテンプレートなど任意の言語のファイルに書かれ、`upgrade` が置き場所を決められない。手順のページで手で書き換えることを示す。レビューで確定する | 予定なし |
| MCP・Claude Code のプラグインからの `upgrade` | 要望に含まれない。プラグインと MCP は #11 が持ち、`upgrade` を MCP に出す要件は持たない | 予定なし |
| 移行の手順の巻き戻し（版を下げる） | 要望に含まれない。手元の版が目標の版より新しいときは止める | 予定なし |
