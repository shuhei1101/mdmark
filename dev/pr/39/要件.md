# 要件

## 要望

mdmark の版が上がったとき、使う側が `mdmark upgrade` で手元の版から目標の版までの移行の手順を版の順に当て、その範囲の変更履歴を見られる。
開発側は、設定・索引のスキーマを変えた版に移行の手順を置き忘れたまま配れない。

<!-- table: data -->

| 項目 | 要件 |
| --- | --- |
| コマンド | `mdmark upgrade [{目標の版}] [--plan] [--yes]` を足す。目標の版を省くと、呼んだ CLI の版を目標にする |
| 手元の版 | 設定ファイルが持つ使う側の版を手元の版とする。手元の版が目標の版より新しいときは何も当てず、原因と直し方の 1 文を出して終了コードを 0 以外にする。同じ版のときは何も当てずに終了コード 0 で終える |
| 移行の手順 | 版ごとに `migrations/{版}/steps.yaml` を置き、手元の版より新しく目標の版以下の版の手順を、版の順に当てる。手順の種類は、設定・索引のキーの名前を変える・キーを足す（値を利用者に聞く指定を持てる）・値を読み替える・文書の印を書き換える・宣言で書けない移行をスクリプトで当てる、の 5 つ |
| 当てる前に示す | `--plan` は何も書き換えず、当てる版ごとの手順・その範囲の変更履歴の行・壊す手順の有無を出す |
| 壊す手順 | 手順に壊す印（`destructive`）があるとき、`--yes` が無ければ当てる前に確かめ、断られたら何も書き換えずに終える |
| 失敗したとき | 当てる前に書き換える対象の写しを取り、手順の途中で失敗したら写しから戻し、失敗した版・手順・理由を出して終了コードを 0 以外にする |
| 成功したとき | 全ての手順を当てた後に `mdmark check` と同じ点検を通し、通ったときだけ設定の版を目標の版に書き換え、写しの場所を出す。点検が通らなければ版を書き換えず、ずれの一覧を出して終了コードを 0 以外にする。途中で止まっても、次の `upgrade` が同じ手元の版から当て直す |
| 変更履歴 | 当てた範囲（手元の版より新しく目標の版以下）の変更履歴の行を出す |
| 開発側の点検 | 設定・索引の JSON Schema（`schemas/`）を前の版のタグから変えたのに、その版の `migrations/{版}/steps.yaml` が無いとき、開発側の検査を通さない。広げるだけの変更は、理由と変えた Schema の SHA-256 を書いた一覧（`no-steps.yaml`）に載せて通す |
| 誤りの扱い | 設定ファイルが無い・読めない、目標の版が版の形でない・存在しない、手順のファイルが読めない・形に合わないときは、何も書き換えず、原因と直し方の 1 文を出して終了コードを 0 以外にする |
| 完了の基準 | 手順を持つ版を 2 つ以上またぐ見本の設定・索引・文書で `upgrade --plan` と `upgrade` を流し、手順が版の順に当たって点検が通り、設定の版が目標の版になる。手順の途中で失敗させると、書き換えた全てのファイルが当てる前の中身に戻る |

<!-- /table -->

`未確定`: 手元の版を持たない設定（v0.3.0 までの `init` が置いた設定）の扱い（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 設定に `version` キーを足して `init` が置く版を書き、`version` が無い設定は `upgrade` が利用者に手元の版を聞く（`--yes` のときは止める） | 手元の版を取り違えずに済む | 初回の `upgrade` で 1 度聞かれる |
| B | `version` が無い設定は、移行の手順を持つ最も古い版より前とみなして全ての手順を当てる | 聞かずに済む | 既に当たっている手順を当て直し、値を壊しうる |

推奨: A

当てる手順は手元の版で決まり、取り違えると移行が設定を壊すため、分からないときは聞く。

`未確定`: 開発側の点検を流す場所（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 配布物のビルド（`npm run build`）の検査に足し、手順の無い版はビルドを失敗させる | CI が無くても、配る前の検査で必ず止まる | ビルドが前の版のタグを読むため、タグを取ってある clone が要る |
| B | GitHub Actions を新設して流す | push のたびに止まる | 今の開発の流れに無い CI の保守が増える |

推奨: A

今の開発側の検査は開発コマンドで流しており、CI は無い。配る前に必ず通るビルドに置けば止め忘れが無い。

## スコープ外

<!-- table: data -->

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 使う側のページに書いた配布物の URL のタグの書き換え | 判断: 含めない。タグは使う側のサーバーのテンプレートなど任意の言語のファイルに書かれ、`upgrade` が置き場所を決められない。手順のページで手で書き換えることを示す。レビューで確定する | 予定なし |
| MCP・Claude Code のプラグインからの `upgrade` | 要望に含まれない。プラグインと MCP は #11 が持ち、`upgrade` を MCP に出す要件は持たない | 予定なし |
| 移行の手順の巻き戻し（版を下げる） | 要望に含まれない。手元の版が目標の版より新しいときは止める | 予定なし |
