# 要件

## 要望

GFM と同じ `[^1]`（本文の参照）と `[^1]: 中身`（定義）、行内の `^[中身]` を脚注として描く。
決まったこと（検討事項 D-45）は Issue の本文と、本文の `## 必読` に挙げた話し合いの記録が正。

- 本文の参照の場所に脚注の番号を出し、ポインター・フォーカスで脚注の中身をツールチップに出す
- 番号を押す（Enter を含む）と、末尾の一覧を開いて該当の脚注へ移る
- 文書の末尾に脚注の一覧をまとめ、一覧は既定で閉じる
- 脚注の番号とツールチップは、用語のツールチップ（破線の下線・波線のマーカー）と見た目で見分けられる
- 印刷では、末尾の脚注の一覧を開いて出す（印刷では閉じた折り畳みを開く今の決まりに揃える）
- 脚注を記載していない文書の見た目は変わらない

`未確定`: 脚注の読み取り方（決める段: モジュール構成設計。ライブラリ選定を挟む）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | markdown-it の脚注のプラグイン（markdown-it-footnote）を採り、出力を mdmark の部品の HTML に組み替える | GFM と同じ読み取りの細部（定義の複数段落・同じ脚注の複数回の参照・定義の無い参照）をプラグインに任せられる | 依存が 1 つ増える。プラグインの出力の HTML を組み替える処理が要る |
| B | 今の記法と同じく、markdown-it のルールを自前で記載する | 依存が増えない。出力を最初から部品の HTML にできる | 定義の中の段落・リスト、参照の番号付けを自前で書き、GFM との差が出やすい |

推奨: A

GFM と同じ書き方で読めることが要件の中心で、読み取りの細部を保守されたプラグインに任せるほうが差が出にくいため。
採るときは package.json と dev/設計書/外部ライブラリ に設計書を追加する。

`未確定`: 設定の `features` に脚注のキーを追加するか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `features` に `footnotes`（既定 `true`）を追加し、文書の `<!-- features: -footnotes -->` で切れるようにする | 他の記法（`callout`・`toc` など）と同じく、使う側と文書ごとに切れる | 設定の JSON Schema に行が増え、`migrations/no-steps.yaml` に行を追加する |
| B | キーを追加せず、常に脚注を描く | 設定が増えない | `[^1]` を文字のまま出したい文書で切れない |

推奨: A

今の記法はどれも `features` で切れ、脚注だけ切れないと使う側の設定の決まりが揃わないため。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 本文・表のセル・図のノードから ID で参照する、再利用できる注釈の記法 | 別の要望。脚注は GFM の書き方で、図のノードと線からの参照・`check` での点検を持たない | #304 |
| `mdmark check` での、定義の無い参照・参照されない定義の点検 | 要望に含まれない。GFM でも定義の無い参照は文字のまま出す | 予定なし |
| タッチ端末で用語のツールチップを外のタップで閉じる | 別の要望 | #284 |
