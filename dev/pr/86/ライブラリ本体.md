## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 確かめる JS | 使う側のブラウザが読む JS（`dist/index.js`・`dist/view.js`・`dist/comments.js`・`dist/viewer.js`）と同じ入口・同じ `BROWSER_TARGETS` で、`minify: false` にして束ねた JS | 配るファイルは今のまま。minify の有無が結論に効かないかを PoC で記録する。`dist/cli.js`（Node 24）は対象外 |
| 確かめ方 | 束ねた JS を ESLint と eslint-plugin-compat で、下限の版に無い API を使っていないかを数える | PoC で成立（`## PoC 結果`） |
| `if` のブロックの中の数え方 | `ignoreConditionalChecks: true` で全て数え、報告の位置を囲む `if` の条件が同じ API の `typeof` の確かめのときだけ外す | `未確定`（決める段: モジュール構成設計。案と推奨は表の下） |
| 下限の版 | `BROWSER_TARGETS` の値から取る | 下限の版を 2 か所に書かない |
| 見つけたとき | API の名前と配布ファイルを出し、終了コード 1 で止める | 配布ファイルの上限超過と同じ止め方 |
| 有無を確かめてから使う API | ソースで `if (typeof X ...)` のブロックの中（`then`・`else`）で使う形に揃え、検査が有無の確かめと読む形にする。早期 return の後ろと三項演算子では使わない。API の名前の単位では除外しない | `src/knowledge/dictionary.ts`・`src/diff/panel.ts` を揃える。分岐で読めない箇所が残る場合だけ、配布ファイルと報告の位置の前後の文字列の単位で除外する |
| 組み込む場所 | `npm run build` で配布物を書いた後に流す | `未確定`（決める段: インターフェース定義設計。案と推奨は要件の `## 要望`） |
| 非機能要件 | 『対応ブラウザ』の `measurement` を確かめ方に合わせて書き換える | 決定値は変えない |

`if` のブロックの中の数え方の論点（eslint-plugin-compat の既定は、条件を問わずどの `if` の中の使用も数えない）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 既定のまま数える | 除外の仕組みが要らない | 無関係な `if` の中で使う下限に無い API を見逃す（`src/` の `if` は約 1,100 箇所） |
| B | `ignoreConditionalChecks: true` で全て数え、元のソースのパスと API の名前の組で除外する | 見逃しが無い | v0.6.0 の `dictionary.ts` の最上位の呼び出しのように、除外したファイルの中の確かめの無い使用も消える |
| C | `ignoreConditionalChecks: true` で全て数え、報告の位置を囲む `if` の条件が同じ API の `typeof` の確かめのときだけ外す | 見逃しが無く、除外の一覧も持たない | 束ねた JS を構文木で読み、報告の位置から囲む `if` を辿る処理を足す |

推奨: C

要件は #50 と同じ穴を塞ぐことで、無関係な `if` の中の見逃しも、除外したファイルの中の見逃しも同じ穴になるため。

PoC 検証の成功条件は、同じ設定（同じ除外）で、v0.6.0 のソースを束ねた JS では `Intl.Segmenter` を見つけて止まり、作業ブランチのソース（`src/knowledge/dictionary.ts`・`src/diff/panel.ts` を PoC ブランチで揃えたもの）を束ねた JS では止まらないこととする。

最小再現コードの要点（[poc/compat.ts](https://github.com/shuhei1101/mdmark/blob/33951d4ab9dc803b8225e71b69c9ccf775a11130/poc/compat.ts)）:

```ts
await build({
  absWorkingDir: root, entryPoints, outdir, bundle: true, format: "esm",
  minify: false, target: BROWSER_TARGETS, plugins: [postcssStubPlugin],
});
const eslint = new ESLint({
  cwd: outdir,
  overrideConfigFile: true,
  overrideConfig: [{
    files: ["**/*.js"],
    plugins: { compat },
    languageOptions: { ecmaVersion: "latest", sourceType: "module" },
    // 束ねた依存が持つ eslint のコメント（他のプラグインの規則の無効化）を読まない
    linterOptions: { noInlineConfig: true },
    settings: { browsers: ["chrome 99", "firefox 98", "safari 16.4"] },
    rules: { "compat/compat": "error" },
  }],
  ignore: false,
});
const reports = (await eslint.lintFiles(files))
  .flatMap((result) => result.messages)
  .filter((message) => message.ruleId === "compat/compat");
```

PR の diff の見どころは、`poc/compat.ts` の束ねと ESLint の設定、`src/knowledge/dictionary.ts`・`src/diff/panel.ts` の確かめを `if` のブロックの中で使う形に揃えた差分、`poc/result.log` の構成ごとの報告。
束ねた依存の中の `eslint-disable` のコメントが他のプラグインの規則を指して「規則が無い」と報告するため、`noInlineConfig` で読まず、`compat/compat` の報告だけを数える。
