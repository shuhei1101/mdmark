# 要件

## 要望

knowledge の規約『タグと用語の登録』の「一致のさせ方」（`matching-01` 一致前の正規化）に、用語・文書の別名の一致を合わせる。

### 正規化

- 一致の前に、照合する辞書の語と本文の文字列の両方へ、NFKC・英字の大文字小文字・前後の空白の正規化をかける
- 全角と半角（`ＡＰＩ` と `API`）、英字の大文字と小文字（`Api` と `API`）の違いだけの語は一致する
- 正規化で吸収できない揺れ（活用形・送り仮名・別の言い方）は、今と同じく `aliases` に列挙して一致させる

### 正規化をかける一致

- 用語の下線とツールチップ（`mount`・`render`）の、索引の `terms`・用語集の表の用語と別名、文書の `aliases`
- やめた言い方（索引の `terms[].avoid` と用語集の表の `avoid=`）の照合と、点検の `avoided_term`
- 参照の表の被参照（`collectReferences` の、参照元の本文に出た参照先の `aliases`）
- 本文の参照の取り出し（`collectMatches`）
- 点検の `duplicate_term`: 正規化した後に同じになる語・別名を重なりとして知らせる
- 辞書の中で、正規化した後に同じになる語は 1 つの語として扱い、今の優先の順（索引の `terms` → 描く文書の表 → ほかの文書の表）で先の用語を使う
- `find_docs` の `text`（題・別名・概要）と `list_tags` の `query`（名前・別名・説明）の含むかの判定も、今の大文字と小文字を区別しない判定に NFKC と前後の空白の正規化を加える

### 変えないこと

- 語の区切り（`Intl.Segmenter`）に揃うところだけを照合し、長い語を先に取る規則
- 下線を引く本文の文字と、本文の位置（行・列）は、正規化する前の本文の文字のまま
- 索引・設定の Schema と、公開関数の引数
- `collectMatches` の結果の `text` は、今と同じく照合した辞書の語（索引・表に記載した表記）を入れる。本文の表記は本文の位置（行・列）から引く

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| やめた言い方を正規表現で書けるようにし、from / to のテストを付ける | 規約の `matching-02` は正規表現の用途を点検に限る決まりで、正規表現を足すことは求めていない。Issue の要望にも含まれない | 予定なし |

| 索引の YAML の `aliases[]` からの別名の登録 | 別の要望 | #125 |
