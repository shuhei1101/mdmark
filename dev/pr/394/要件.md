# 要件

## 要望

リポジトリの文書・コードのコメント・画面と CLI に出る文言から、knowledge の対応表が NG とする単語を無くす。

### 正とする規約

| 対象 | 正 |
| --- | --- |
| 置き換える単語と置き換え先 | knowledge の対応表 [AI slop の単語の対応表](https://github.com/shuhei1101/knowledge/blob/406be9c/docs/word-list/word-list-ai-slop.yaml) の `entries`（`ng` → `ok`。ヒットは `pattern` と `allow` で決める） |
| 文章の冗長な言い回し・推量 | 規約 [文章の書き方](https://github.com/shuhei1101/knowledge/blob/406be9c/docs/rule/convention-writing-style.yaml) の「文章を追加した後の確認表」 |
| 対応表に無い単語 | 同規約の「用語の選び方の原則表」と判定フローチャート [用語の選び方](https://github.com/shuhei1101/knowledge/blob/406be9c/docs/flowchart/flowchart-word-choice.yaml) |
| 画面の操作の単語・ボタン・メッセージの書式 | 規約 [入力と文言](https://github.com/shuhei1101/knowledge/blob/406be9c/docs/rule/ui-input-wording.yaml) |

### 修正の決まり

- `ok` が複数ある単語は、文脈で 1 つを選ぶ（「形」はスキーマ・構造、形状の意味なら形状）
- 用語集（`docs/リファレンス/用語集.md`）に載る用語の置き換え先は、用語集で 1 つに決め、全てのページ・コード・画面で同じ単語にする
- ファイル名・フォルダ名に NG の単語を含むファイル・フォルダは改名し、リンク・目次（`index.yaml`・`README.md`）・`files.yaml`・設計書の参照・シナリオの対応テストファイル・E2E のテストファイル名を合わせる
- 見出しを変えたら、その見出しへのアンカーのリンクを合わせる
- `schemas/` の JSON Schema の説明を変えたら、`migrations/no-steps.yaml` に行を追加する
- YAML の設計書は、置き換えスクリプト（`作業/reword.py`）で文字列の値だけを修正し、参照（`callers`・`decided_by`・`refs`・`test`・`page`）とパスは改名と一緒に修正する

### 用語と主語の呼び名の置き換え先

用語集の用語と、設計書が繰り返し使う主語の呼び名は、次の単語に統一する。

<!-- table: data -->

| 元の単語 | 置き換え先 |
| --- | --- |
| 印 | マーカー（範囲のマーカー・閉じのマーカー・コメントのマーカー） |
| 知らせの枠 | 通知ブロック（読み込み中の枠は読み込み中のブロック） |
| 書き方の警告 | 記載の警告 |
| 手元の版 | 手元のバージョン |
| 使い方集 | ガイド |
| 使う側 | 利用側 |
| 文書を書く人 | 文書の作成者 |
| 読む人 | 読者 |
| コメントの読み書きの関数 | コメントの読み込みと保存の関数 |
| 読み上げの名前 | スクリーンリーダー向けの名前 |
| 変更を見る（ボタン） | 変更表示 |
| コメントを書く（aria-label） | コメント追加 |

<!-- /table -->

`読む` は、プログラムがファイルや配布物を取り込む意味では `読み込む`、人や AI が文書を読む意味では `参照する` にする。
`書く` は、ファイル・クリップボード・標準エラーへの出力では `書き込む`、文書への記述では `記載する` にする。
`〜し直す` は `もう一度〜する`（`描き直す` は `再描画する`、`読み直す` は `再読み込みする`）にする。

対応表の `allow` に無いが、用語・慣用の複合語として残す単語（`折り返す`・`通し番号`・`取り消し線`・`受け渡し`・`積み上げ`・`使い回す`・`控えめ`）は、件数の確認で残す箇所として記載する。

### 終わりの条件

- 正の対応表で上の対象の範囲を数えた件数が、スコープ外として残す箇所を除いて 0 件になる
- `集計/reposcan.py` と正の対応表で数えた修正前後の件数を、PR に記載する
- 単体・結合・E2E のテストと lint・型検査が pass する

`未確定`: 画面・CLI・VS Code の通知に出す用語の置き換え先（決める工程: 画面設計。ユーザーの確認は承認確認で取る）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 用語集の用語は用語集で 1 つに決めて統一し、それ以外は文脈で `ok` から選ぶ | 同じものを同じ単語で呼べ、文として自然になる | 単語ごとに選ぶ手間がかかる |
| B | 全て `ok` の先頭の単語に置き換える | 機械的に置き換えられる | 「返す」→「返却」のように文脈に合わない箇所が出る |

推奨: A

規約『入力と文言』は同じものを同じ単語で呼ぶことを求めており、用語集の用語を 1 つに決めれば画面・文書・コードで呼び名が統一される。

公開ドキュメント（`docs/`）のファイル名・フォルダ名も改名し、リンクを合わせる。公開済みの URL が変わってよい（確認ログ「公開ドキュメント（docs/）のファイル名・フォルダ名の改名」）。
