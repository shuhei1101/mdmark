# 要件

## 要望

文書を書く人と AI が、図・部品を一から書かずに mdmark の共通の部品と図の見た目の決まりで描け、使う側に固有の CSS・部品をその場所の文書にだけ当てられる。
基盤も、使う側が足す JavaScript も、型の点検とテストを通してから使える。

<!-- table: data -->

| 項目 | 要件 |
| --- | --- |
| 基盤の点検 | 図・部品の基盤は TypeScript で書き、型の検査・lint・単体・結合・E2E（Playwright）を通して JavaScript の配布物にする |
| 使う側の点検 | 使う側が足す JavaScript は変換を挟まず `// @ts-check` と JSDoc で書き、配布物の型定義に対して `tsc --noEmit` で点検できる。型を誤った JavaScript は点検で落ちる |
| 崩れの確かめ | 基盤の部品を変える・足すときは、テストを直して全部を回し、部品のストーリーと見本のページのスクリーンショットを撮って崩れが無いことを確かめる |
| 共通の定義 | フロー図・シーケンス図・グラフの部品と、色・文字・ライト / ダークの CSS 変数を基盤が持ち、どの文書でも使える |
| 文書に書くもの | 文書には部品の定義（JSON）だけを書き、描くのは共通の部品か固有の部品にする。文書に書いた任意のスクリプトは動かさない今の条件（D-22、`render` のサニタイズ）を保つ |
| 固有の定義 | 使う側に固有の CSS と部品は、その場所の文書にだけ当たる |
| 作り方の手順書 | AI が HTML を作るときに読む手順書と、HTML の書き方の決まりの資料を持つ。HTML は図・チャートなど見た目のあるものを描くときだけ使い、文章は Markdown で書く（D-44） |
| 操作できる部品 | スライダー・グラフ・「今の値を写す」ボタン（値を JSON にしてクリップボードへ写す）の作り方を手順書に含める。置いたら Playwright で動きを確かめ、スクリーンショットを撮って見るまでを手順に入れる（D-49） |
| 見本 | テンプレートは持たず、部品と見本のページ（部品を組み合わせたページ）を持つ |
| 図の枠と層 | システムの内側を大きな枠で囲み、外部のシステムは枠の外に置く。内側は上から LLM・意思決定モデルなどのノード、MCP・スクリプトなどの処理、データの 3 層で、各層は何行でもよく、層の箱の色をうっすら背景に敷いて分ける。配置は自動配置のライブラリを使わず grid に手で置く |
| 時系列とループ | 時系列は左から右。ループの戻りは上か下の 1 本の帯だけを通し、破線と戻り先のラベルを付ける |
| 題と凡例 | 図ごとに題名・範囲・更新日と凡例を付け、色・形・線・矢じりの意味を全て凡例に書く。線の種類は色と模様（破線の間隔・太さ・矢じり）の組で分け、色だけで分けない |
| 線の交差 | 交差は箱の並べ替えで減らし、残った交差は横の線が縦の線を飛び越える（line jump）に統一する。線どうしが重なるときは少しずらす |
| 矢印と箱のツールチップ | 矢印には入力の要約を書き、詳細をツールチップに出す。箱の中の用語には用語集の意味を点線の下線つきのツールチップで出す。LLM・スクリプトの箱には入力・処理・出力をツールチップで出し、ツールチップのある箱には印を付ける |
| ツールチップの振る舞い | ホバーとフォーカスの両方で出し、Esc で消え、上に乗っても消えない（`role="tooltip"`・`aria-describedby`）。理解に必須の決まりは入れず、用語集は図の外にも置く |
| 文字の選択と移動 | 文字の上ではカーソルが I になって文字を選べ、それ以外ではドラッグで図を動かす。ドラッグ中は文字を選ばせない。ドラッグ以外の移動手段（矢印キー・ボタン）も置く |
| 拡大・縮小 | 開いたときは全体が収まる倍率。拡大・縮小は図の右上のボタンとキーの `+`・`-`・`0` だけで行い、ホイールは普通のスクロール（Shift＋ホイールで横）にする |
| 構成図とフローチャートの決まり | 構成図と処理の順番を描くフローチャートは、作り方の決まりを別のリファレンスに分ける |
| 完了の基準 | 見本のページ（フロー図・シーケンス図・グラフ・操作できる部品・固有の部品と CSS を当てた文書）で、図の見た目の決まりと操作の各項目が E2E で確かめられ、非機能要件の対応ブラウザで通る。使う側の雛形の JavaScript が `tsc --noEmit` を通り、型を誤った例が落ちる |

<!-- /table -->

`未確定`: 図の部品の仕組みと共通の図の部品をどの Issue で作るか（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 文書に部品の定義を書く仕組みと、共通の図の部品（フロー図・シーケンス図・グラフ）を #21 で作る。#6 は HTML のコードブロックの表示・Chart.js のチャート・`data-hint` をこの仕組みに載せる | 図の見た目の決まりを部品の描き方で守らせ、E2E で確かめられる | #6 の本文の範囲（図の部品・`registerComponent()`）を #21 へ移す書き直しが要る |
| B | #21 は図の見た目の決まり・CSS・手順書・点検だけを持ち、部品は #6 で作る | #6 の範囲を変えない | #21 の完了の基準を確かめる部品が無く、#6 が #21 を依存に持つため順序が逆になる |

推奨: A

#6 は計画で #21 を依存に持ち、決まりを当てる先の部品が #21 の中に無いと決まりを確かめられないため。

`未確定`: 固有の部品の足し方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 今ある `registerExtension` で足す。部品のモジュールは使う側のページか設定の `extensions` が読み、文書には印と部品の定義だけを書く | D-22 と食い違わず、新しい公開関数を増やさない | 部品の定義（JSON）を印の引数より長く渡す口を足す必要がある |
| B | #6 の `registerComponent()` を新しく作り、custom element として足す | #6 の一案のとおりになる | `registerExtension` と同じ役目の公開関数が 2 つになる |

推奨: A

文書に書いたスクリプトを動かさない条件のまま、使う側の部品を足す口が既にあるため。

`未確定`: 固有の CSS と部品を当てる「その場所」の範囲（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 設定ファイル `mdmark.config.yaml` 単位。その設定の `theme`・`extensions` が、その設定で描く・書き出す文書だけに当たる | 今の設定のキーの延長で、使う側のワークスペースごとに分かれる | 1 つの設定の中でフォルダごとに分けられない |
| B | 索引のフォルダ単位で CSS と部品を指す | 1 つのワークスペースの中でも分けられる | 索引の形を変え、点検の対象が増える |

推奨: A

要望の「利用する側（ワークスペース）」の単位が設定ファイルの単位と一致するため。

`未確定`: 拡大・縮小とホイールの決まりをチャートにも当てるか（決める段: 単一ユースケース設計）

#6 は「Chart.js のチャートは拡大・縮小とドラッグで移動できる（chartjs-plugin-zoom など）」「普通の HTML には拡大・縮小のボタンを付けない（D-43）」としている。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | この Issue の決まり（右上のボタンとキー、ホイールは普通のスクロール）を図とチャートの両方に当て、D-43 は部品でない普通の HTML に限る | 文書の中の拡大・縮小の操作が 1 つに揃う | #6 のチャートの操作の一案を書き直す |
| B | 図にだけ当て、チャートの操作は #6 で決める | #6 の一案を変えない | 図とチャートで拡大・縮小の操作が分かれうる |

推奨: A

ホイールでの拡大・縮小は文書のスクロールを奪い、図とチャートで操作が違うと読む人が迷うため。
