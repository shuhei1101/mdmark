# 要件

## 要望

Claude Code のプラグイン（`plugin/`）にスキルを 2 つ置き、端末とリポジトリのセットアップを、利用者に確認しながら Claude Code が進められるようにする。

| スキル | 単位 | すること |
| --- | --- | --- |
| `global-setup` | 端末ごとに 1 回（入れ直し・端末の移行・プラグインの更新の後にも使う） | 端末の設定のパスを決める → 端末の設定があればバージョンを確かめて移行し、無ければ雛形から作る → パスが既定と違えば `~/.claude/settings.json` の `env` に `MDMARK_CONFIG` を書く → MCP の常駐サーバーを起動して `tools/list` でつながることを確かめる → フックが動くことを確かめる → 作ったもの・書いたキー・結果を示す |
| `setup` | 文書のフォルダごと | 文書のフォルダに `mdmark.config.yaml` を作る・修正する |

- 端末の設定（`${XDG_CONFIG_HOME:-~/.config}/mdmark/settings.yaml`、`MDMARK_CONFIG` で上書き）は [#163](https://github.com/shuhei1101/mdmark/issues/163) で入った読み方をそのまま使い、読み方は変えない
- 設定の項目（機能のオン・オフ・端末の設定の `config` の切り替え・索引の場所・使う側の CSS など）は、設定のリファレンスのキーごとに今の値と既定を示し、利用者に 1 つずつ確認してから書く
- 常駐サーバーの状態とログを `${XDG_STATE_HOME:-~/.local/state}/mdmark` に置き、環境変数 `MDMARK_STATE_DIR` で上書きできるようにする
- 常駐サーバーが起動していなければ、tmux のセッションの中で起動する。セッションが既にあれば作らず、ポート（`MDMARK_PORT`、既定 8782）が待ち受けているかで起動を確かめる
- tmux のセッション名は既定値を持ち、端末の設定のキーで変えられる（設定の Schema を変えるので、`migrations/no-steps.yaml` に行を置く）
- 常駐サーバーが起動しているか・tmux のセッション名・起動の仕方を、SessionStart のフックか MCP の説明文で伝える。起動していないときは `global-setup` で起動できることを伝える

常駐サーバーの起動の仕方（単一ユースケース設計で推奨案 A に決定）

knowledge の規約『ローカルサーバーの立て方』は、必ず動いていてほしい常駐サーバー（MCP など）を systemd --user で起動し、tmux は dev サーバーに使うとしている。
Issue は tmux で起動するとしている。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | tmux のセッションで起動する（Issue のとおり） | systemd の無い端末（macOS・systemd を有効にしていない WSL）でも同じ手順で動く。止める・ログを見るのが `tmux` の操作で済む | 端末の再起動の後は、SessionStart の案内を見て `global-setup` で起動し直す |
| B | systemd --user の unit を `global-setup` が作り、tmux は systemd が無い端末だけで使う | 規約のとおり、端末の起動で自動で動く | 起動の仕方が端末で 2 つに分かれ、スキル・案内・テストが倍になる |

推奨: A

Issue が起動の仕方を tmux と決めており、規約の systemd は WSL の常駐を前提にしている。
mdmark のプラグインは macOS でも使うため、どの端末でも同じ手順で動く tmux を既定にし、systemd の unit は起票予定としてスコープ外に置く。

tmux のセッション名の既定（単一ユースケース設計で推奨案 A の `mdmark-mcp` に決定）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `mdmark-mcp` | 規約『ローカルサーバーの立て方』の `{リポジトリ}-{役割}` の付け方と役割名 `mcp` に合う | 今の手元の `mdmark-server` と名前が変わる |
| B | `mdmark-server`（Issue の一案） | 今の手元のセッションと同じ | 規約の役割名と合わない |

推奨: A

Issue の一案は「確かめてはいない」としており、セッション名は規約の付け方に揃える。

起動の案内は、常駐サーバーが待ち受けていないときだけ SessionStart のフックで 1 行を出し、起動しているときの tmux のセッション名は MCP の `instructions` に書く（[確認ログ](./確認ログ.md)）。
[#293](https://github.com/shuhei1101/mdmark/pull/293) で SessionStart のフックを外した理由（mdmark を使わないセッションにも毎回文が入る）を、起動しているときには戻さない。

tmux が無い端末の扱い（単一ユースケース設計で推奨案 A に決定）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `global-setup` は起動せず、端末で `mdmark serve` を開いたまま動かす手順を示す | 起動の仕方が tmux 1 つに揃う | Windows のネイティブの端末では自動で起動しない |
| B | tmux が無ければ別の常駐の仕方（バックグラウンドの起動）を使う | どの端末でも起動する | 規約『ローカルサーバーの立て方』が禁じる tmux・systemd の外の常駐になる |

推奨: A

## スコープ外

<!-- table: data -->

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| systemd --user の unit で常駐サーバーを起動する | 推奨の案 A では tmux を既定にする。規約『ローカルサーバーの立て方』に合わせるかは、tmux の起動が入った後に決める | 起票予定 |
| knowledge の判定フローチャート『設定値の置き場所』と規約への、既定のパスと環境変数の名前の付け方の記載 | knowledge のリポジトリの作業で、この PR に依らず成り立つ | 予定なし |
| rule-inject・alias-inject の `global-setup`・`setup` | それぞれのリポジトリの作業で、この PR に依らず成り立つ | 予定なし |
| 端末の設定のパスと `MDMARK_CONFIG` の読み方 | [#163](https://github.com/shuhei1101/mdmark/issues/163) で入った | 予定なし |
