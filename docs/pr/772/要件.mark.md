### #760 カーソルを help にしない

- 再現: develop の `src/index.css` では、ER 図のノートのマーカー（`.map-er-note`）とクラス図のノートのマーカー（`.map-class-note`）が `cursor: help` を持つ。ほかの部品の CSS・TypeScript に `help` のカーソルは無い
- 2 つの規則から `cursor: help` を削除し、ツールチップを持つほかの要素と同じカーソルにする
- 部品設計・インターフェース定義の期待値に、ツールチップを持つ要素の `cursor` の計算値が `help` でないことを、ノートのマーカーにも入れる

### #764 線の押せる範囲

- 対象は `.map-wire-hit` を持つ全ての線（構成図の上に描く図の線・同じノードへの線・シーケンス図のメッセージの線）。シーケンス図のライフライン（`.map-lifeline-hit`）は縦の直線で、囲む矩形が押せる範囲と一致するため変えない
- 線の押せる範囲を、区間ごとの要素など、要素を囲む矩形が実際の押せる範囲と一致する作りにする
- 線にポインターを重ねたときの強調・ツールチップ・フォーカスと読み上げの名前（今の `tabindex`・`role="button"`・`aria-label` は 1 本の線に 1 つ）・ドラッグで区間を動かす操作は、今と同じに動く

線 1 本の押せる範囲は、線ごとの `g.map-wire-hit` の中に区間ごとの帯（区間に沿った幅 14px の矩形）を並べ、フォーカスと読み上げの名前は最も長い区間の帯だけが持ち、フォーカスしたときは全ての区間の帯を強調する（インターフェース定義『文書を描く』の制約「map の線の押せる範囲」）。
axe の target-size は要素を囲む矩形で判定するため、`g` にフォーカスと名前を持たせると `g` を囲む矩形が線の全体になり、今と同じ誤検出が残る。区間ごとにフォーカスを持たせると Tab の止まり先が区間の数だけ増えるため、最も長い区間の帯だけに持たせ、Tab の止まり先を線 1 本に 1 つのままにする。シーケンス図のメッセージの線は、今と同じくフォーカスを持たない。

### #766 map の図の文字

- ノードの名前（`.mdmark-diagram-node-name`）・種類の行（`.mdmark-diagram-node-kind`）・線のラベル（`.mdmark-diagram-label`）の書体・大きさ・太さを、mermaid の図（部品『mermaid の図』）に近い細めで小さめにする
- map が描く全ての種類（構成図・ER 図・状態遷移図・クラス図・アーキテクチャ図・C4 図・軸と格子の配置の図）と、map で描く mermaid のコードブロックに同じ値を適用する
- 文字が小さくなる分、ノードの大きさを決める配置の計算（名前の幅と行の高さ）を合わせる

名前 13px・種類の行と線のラベル 11px、どれも標準の太さ（400）にする（[確認ログ](./確認ログ.yaml) の推奨案 A）

### #765 マインドマップの項目

- 項目ごとに枠線を付ける（根・項目とも）
- 短い項目名（`map`・`mdmark`）を途中で折り返さない。項目の幅を名前の幅から決め、長い名前だけを折り返す
- 文字の大きさ・太さを #766 と揃える
- フォーカスの操作（項目の選択・枝の開閉と中へ入る持ち手）の使いづらさを、モックで具体化して直す

名前の文字の上を押しても項目を選び（ドラッグで文字を選んだときは選ばない）、ポインターを重ねた項目と選んだ項目の面に枝の色を敷く（[確認ログ](./確認ログ.yaml) の推奨案 A）

### #767 線の出る位置と間隔

- 同じノードの同じ辺から出入りする複数の線の端を、辺の上で線の数に応じてずらす（辺の中点 1 か所に集めない）
- 端は相手の並びの順に 16px 間隔で並べ（辺に収まらなければ辺の長さを等分）、並んで同じ向きに走る区間も 16px 離す（[確認ログ](./確認ログ.yaml) の推奨案 A）。ガイド『構成図の決まり』の「線どうしが同じ向きで重なるときは、4px ずつずらす」は今の配置に無いため、この値で書き直す
- [変更箇所の由来](#変更箇所の由来) のとおり、線どうしの重なりは #663 の重み（`usedCost`）の追加の後も起き続けているため、重みの値の調整で直さず、線の端の割り当て（`portsOf`）と並んだ区間の間隔を取る処理を配置の設計に足す
- 線をドラッグで動かした後の線と、補足の `layout` で辺を指定した線（アーキテクチャ図の `L`・`R`・`T`・`B`）にも、同じずらし方を適用する

### #769 VS Code 拡張機能の書き出し

- 書き出す HTML（IF-472-15）・印刷する HTML（IF-472-16）・ブラウザで開く HTML（IF-472-18）は、同じ組み立てを使用するため、3 つとも元の Markdown を埋めない
- 書き出すときに描いた HTML と `toPureMarkdown` の純粋な Markdown を埋め、開いたときは `mount` の `opts.rendered`・`opts.pureMarkdown`（#753 で追加。IF-472-35）で描く
- 外部ライブラリ・拡張のマーカーは、CLI の書き出しと同じく、マーカーの場所を HTML に残して開いたときにモジュールで描く
- 取り込み（`include`）の本文も、描いた HTML の中に入れ、取り込む文書の Markdown を埋めない

書き出すときに、決めたバージョンの jsDelivr の `dist/index.js` を取得して拡張機能のホストで読み込み、その `render`・`toPureMarkdown` で描く（インターフェース定義『HTMLに書き出す』の制約「バージョンと描く処理」）。
開いたときに読み込む配布物と描いたバージョンを一致させるためで、取得した `dist/index.js` はバージョンごとに拡張機能の保存先に置いて使い回す。
配布物を取得できないときと、`opts.rendered` を持たないバージョンのときは、書き出さずに通知を出す（通知の文言は画面設計で決める）。

### #748 同じ記載を描く処理の洗い出し

- `src/` の mermaid 以外の部品（`*.part.ts`・`*.syntax.ts`・`*.interact.ts` と `src/render/`）で、同じ記載を描く処理が 2 つある箇所をモジュール構成設計で洗い出し、モジュール構成の一覧にして reviewer に確認を受ける
- 洗い出した箇所は、新しい方に寄せて古い方とその設計書・テストを削除する。寄せる先の部品が描く結果が変わる箇所は、単一 UC・部品設計の期待値に反映する
- マーカーの今の書き方を読む処理（`src/render/legacy-marks.ts`）は [#479](https://github.com/shuhei1101/mdmark/issues/479) が持つため、洗い出しの一覧には載せるが削除しない
- 対象が無ければ、洗い出した範囲と結果を PR に報告する
