# 要件

## 要望

- 利用側のページが `dist/index.js` を 1 枚の HTML に埋めて読み込むときに、mermaid のモジュールも埋めて mdmark に指定できる公開の手段を用意する
- 指定したときは、mermaid で描くコードブロックがあっても設定の `mermaid.url` へ要求せず、指定したモジュールで図を描く
- 指定しないときは、今と同じく `mermaid.url` から読み込む。書き出した HTML の起動の処理（`setEmbeddedMermaid` で指定する）の描き方は変えない
- 指定したモジュールの構造の確認（既定の export が `initialize` と `render` を持つか）は、`mermaid.url` から読み込むときと同じにする
- 手段は、#655 の部品の読み込みの手段（`setPartModuleLoader`。部品を初めて使用するときに 1 回だけ呼ぶ関数を指定する）に合わせる

`未確定`: 公開の手段の形（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `setPartModuleLoader` の名前に `"mermaid"` を足し、mermaid のモジュールを返却する関数を指定する | 部品と同じ 1 つの関数で指定でき、mermaid で描くコードブロックがある文書でだけ関数を呼ぶ | 名前ごとに確認する export の形が変わる（mermaid は既定の export） |
| B | 今の `setEmbeddedMermaid(module)` をそのまま公開する | 内部の変更が最も少ない | mermaid を使用しない文書でも、利用側が先に mermaid を読み込んでおく必要がある。部品の指定の形とそろわない |
| C | mermaid 専用の公開関数（関数を指定する形）を新しく置く | 部品の名前の検証と分けられる | 公開関数が増え、部品と同じ形の指定が 2 つに分かれる |

推奨: A

部品と同じ関数・同じ遅延の読み込みにそろえると、利用側の手順が 1 つで済み、mermaid（5 MB ほど）を使用しない文書では読み込まずに済むため。
