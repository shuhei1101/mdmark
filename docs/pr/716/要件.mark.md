# 要件

## 要望

mdmark-style の返答の描き換えで、次の mdmark の機能を共通スタイルで描く。
どの部品も、マーカーの文字（`<!-- ... -->`・`badge:` などの記法の頭）を画面に出さない。

<!-- table: {"kind": "data"} -->

| mdmark の機能 | Claude Code の画面での描き方 |
| --- | --- |
| 行の詳細 | 表の行ごとに開閉の Button を描き、押すとその行の下に詳細の中身を描く |
| ステップ | 番号付きリストの番号を、共通スタイルの色の付いた手順の番号として描く |
| ファイルツリー | 言語 `tree` のコードブロックを罫線のツリーとして描き、注釈を薄い色で描く。開閉とアイコンは描かない |
| バッジ・文字の色・蛍光ペン・キー | バッジ・文字の色は色の名前の文字色、蛍光ペンは色の名前の背景色、キーは `[Ctrl]` の囲みで描く |
| タブ・段組み・カードの格子・wide の範囲・ビュー・CSV の表 | 切り替え・横並びにせず、区切りごとの中身を区切りの名前の見出しつきで縦に並べる。ビュー・CSV の表は表の部品で描く |
| 図と表の番号 | 番号を付けた表の前に、mdmark の描いた文書と同じ番号の文字を描く |

<!-- /table -->

色は、Web の描いた文書と同じ値を共通スタイルの定義から取る。
部品ごとに設定の `parts` のキーを追加し、`false` のときはその部品を今の描き方（Claude Code の `Markdown` 部品）のまま描く。

`未確定`: 追加する `parts` のキーの分け方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 上の表の行ごとに 1 つのキーを追加する | 設定の数が少ない | バッジと蛍光ペンなど、行の中の機能を別々にオフにできない |
| B | mdmark の機能ごとに 1 つのキーを追加する | 機能ごとにオフにできる | キーが多く、設定の見本が長くなる |

推奨: A

Issue の表の行が、描き方をまとめて決めた単位で、行の中の機能は同じ描き方を共有するため。

`未確定`: セッションの開始に追加するマーカーの記載方法の説明に、追加する部品のマーカーをどこまで含めるか（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 追加する部品のマーカーを全て含め、合計の文字数の上限を見直す | モデルが全ての部品を返答に記載できる | セッションごとの文脈が増える |
| B | 返答で使用する見込みの高いステップ・ファイルツリー・バッジだけを含め、今の上限に収める | 文脈の量が変わらない | 含めない部品は、モデルが記法を知っているときしか描かれない |

推奨: B

返答でタブ・段組み・ビューを使用する場面は少なく、文脈の量を増やさずに主な部品を使用できるため。
