# 要件

## 要望

`vscode-v{X}.{Y}.{Z}` のタグの push で、`vscode-release.yml` が GitHub Release に .vsix を添えた後、同じ .vsix を Open VSX へ `ShuheiNishikawa.mdmark-vscode` として公開する。

- 認証は Open VSX の trusted publisher（GitHub Actions の OIDC トークン）で行い、長期のトークンをリポジトリのシークレットに置かない
- ワークフローの `permissions` に `id-token: write` を加える
- タグと `vscode/package.json` の `version` が合わないときは、今と同じく .vsix を作らず、Open VSX へも公開しない
- Open VSX に同じバージョンが公開済みのときは、ワークフローを失敗させる（同じバージョンは上書きできない）
- 公開の流れは shuhei1101/knowledge#175 の規約『VS Code 拡張機能の配布』（自動にできる公開先は CI、できない公開先は手動）に従う
- Marketplace へはこの PR では公開しない。設計書とワークフローには、Marketplace が OIDC に対応したら同じジョブに `vsce publish` の工程を加える旨を残す

Open VSX の初回の公開と trusted publisher の登録は、ユーザーが次の順に手で行う（拡張機能が無い間は trusted publisher を登録できず、登録にはネームスペースの所有者であることが要る。Open VSX の wiki [Trusted Publishing](https://github.com/eclipse/openvsx/wiki/Trusted-Publishing) の前提条件）。

1. ネームスペース `ShuheiNishikawa` の所有権を [EclipseFdn/open-vsx.org](https://github.com/EclipseFdn/open-vsx.org/issues/new/choose) の Issue で申請する（[Namespace Access](https://github.com/eclipse/openvsx/wiki/Namespace-Access)）
2. Publisher Agreement に署名済みかを確かめる
3. アクセストークンで .vsix を手で公開する
4. trusted publisher を登録する（リポジトリ `shuhei1101/mdmark`・workflow `vscode-release.yml`・拡張機能 `mdmark-vscode`・environment なし）

2 回目以降の公開を `vscode-v*` のタグでワークフローが行う。
