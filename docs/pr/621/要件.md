# 要件

## 要望

1. 使用する側が jsDelivr の `@develop` と `npx github:shuhei1101/mdmark#develop` で参照したときに、develop の先頭の commit の配布物（`dist/`）と Claude Code プラグインの生成物（`plugin/`）が動く
2. develop へ commit が入ってから、`dist/`・`plugin/` がその commit を含めて再作成されるまで、人の操作を挟まない
3. `npx github:shuhei1101/mdmark#develop` で入れるときも、開発用の処理（`tools/eslint/` の依存の導入）を実行しない（[SC-472-5](https://github.com/shuhei1101/mdmark/blob/35edd638/docs/scenario/SC-472-5.yaml) の保証を保つ）
4. `mdmark.config.yaml` の `version` に develop の最新を表す値を記載でき、`mdmark check`・Schema の検査が通る
5. タグ（`v{x}.{y}.{z}`）・commit を指定した今の参照と `version` はそのまま使用できる
6. 公開ドキュメントに、既定の参照（develop の最新）と、固定するときの書き方を記載する

`未確定`: develop の配布物を最新に保つ方法（決める工程: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | develop への push で GitHub Actions が `npm run build` を実行し、`dist/`・`plugin/` に差分があれば develop へ commit する | jsDelivr と npx の両方に有効になる。使用する側は何も入れない | develop に CI の commit が追加される |
| B | `package.json` の `prepare` でビルドする | develop に commit が増えない | jsDelivr は `prepare` を実行しないため有効にならない。npx で開発の依存を入れることになり要望 3 を満たさない |

推奨: A

B は要望 1 の jsDelivr と要望 3 を満たせない。

`未確定`: `version` に記載する develop の最新を表す値（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `develop` | jsDelivr・npx の参照と同じ単語で、何を指すかが一意 | - |
| B | `latest` | 一般的な語 | VS Code 拡張機能の `mdmark.version: latest` は「タグ一覧の最新」を指し、同じ単語で別のものを指す |

推奨: A

参照の書き方と同じ単語にそろい、`latest` との取り違えが起きない。

`未確定`: 手元のバージョンが develop の最新のときの `mdmark upgrade` の扱い（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 手元が `develop` のときは移行の手順を適用せず、固定したバージョンを記載してから呼ぶよう出して終了コード 1 で終わる | 適用した手順の記録が無いまま二重に適用する事故が起きない | develop を追う間に入った壊す手順は、使用する側が固定し修正するまで適用されない |
| B | develop の CLI が `migrations/next/` まで適用し、`version` は `develop` のまま残す | develop を追ったまま手順が適用される | どこまで適用したかが残らず、次の呼び出しで同じ手順を再適用する |

推奨: A

移行の手順の比較は手元のバージョンが順序を持つことが前提で、`develop` はその順序に乗らない。

`未確定`: develop のビルドの CLI で呼ぶ `mdmark upgrade` の目標のバージョン（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `migrations/next/` まで適用し、`version` を `develop` にする | 適用後の点検が通る | 次に固定し直すまで、手元が `develop` で upgrade が止まる |
| B | 目標は `version.ini` の値のままにし、`migrations/next/` に手順があるときは止めて、タグの CLI で呼ぶよう出す | 記録の無い適用が起きない | develop の CLI では upgrade できない場面がある |

推奨: B

手元が `develop` のときに止める判断と同じく、記録が残るバージョンでだけ手順を適用する方針にそろう。

`未確定`: develop のビルドに埋めるバージョン（`version()`・`--mdmark-version`。決める工程: モジュール構成設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `version.ini` の値にビルドメタデータとして develop と短縮 SHA を添えた値（例: `v0.13.0+develop.{短縮 SHA}`。短縮 SHA は生成物を commit する前の、ビルドの元の commit） | 動いている配布物がどの commit かを使用する側が確認できる | バージョンの書式を検査する箇所（ビルド・VS Code 拡張機能のタグの照合）を合わせる |
| B | `version.ini` の値のまま | 変更が少ない | 前回のタグと develop の配布物を見分けられない |

推奨: A

`未確定`: release → develop のバックマージで `dist/`・`plugin/` が競合したときの扱い（決める工程: モジュール構成設計）

推奨: develop 側を採って取り込み、取り込みの push で CI が再作成する。
