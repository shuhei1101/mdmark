# 要件

## 要望

マーカーの今の書き方（名前の後ろが `{` で始まらない引数）を JSON のオブジェクトへ変換して描く処理を削除する。

- `src/render/legacy-marks.ts` と、描く処理（`src/render/marks.ts`）の `convertLegacyArgs` の呼び出しを削除する
- 記法・機能・ページのマーカーの今の書き方の引数は、描くときに適用しない。マーカーの場所に記載の警告を出し、JSON のオブジェクトでの記載と `mdmark upgrade` を案内する
- 点検の `legacy_mark` の扱いを決め、点検・`mdmark upgrade` の移行の後の点検・設計書・ガイド・テストを合わせる
- `mdmark upgrade` は、手元のバージョンが `v0.11.0` より前の設定・索引・文書を、今までどおり JSON のオブジェクトへ書き換える（`migrations/v0.11.0/legacy-marks.js` を使用する）
- `scripts/build.ts` は `src/render/legacy-marks.ts` が無いとき、出していないバージョンのフォルダへ `legacy-marks.js` を記載しない（今の `buildLegacyMarks` の決まりのまま）

`未確定`: 点検の `legacy_mark` の扱い（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 点検は今の書き方の引数を `legacy_mark` のまま 1 件のずれにし、内容で `mdmark upgrade` を案内する。描く処理は引数を適用せずに記載の警告を出す | `v0.11.0` より前から上げた利用者が、点検の結果から `mdmark upgrade` へ辿れる。`mdmark upgrade` の移行の後の点検の除外（`legacy_mark`）もそのまま使える | 名前の後ろが `{` で始まらない引数を見分ける処理（`readMarkArgs` の `legacy`）が残る |
| B | 今の書き方の引数を JSON として参照できない引数（`readMarkArgs` の `invalid`）として扱い、`legacy_mark` を削除する | 引数の見分けが JSON とそれ以外の 2 通りになり、処理が減る | 点検の内容が JSON の構文の誤りになり、`mdmark upgrade` で書き換えられることが伝わらない |

推奨: A

今の書き方の文書は `mdmark upgrade` で書き換えられるため、点検が書き換えの手段へ案内するほうが利用者が修正しやすい。
