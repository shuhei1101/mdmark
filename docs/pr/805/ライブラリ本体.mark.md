### 変更方針

<!-- table: {"kind": "data"} -->

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 失敗の通知 | `develop-dist` の job が失敗したら、`gh issue` で失敗した実行の URL と元の commit を持つ Issue を `確認:task-planner` を付けて起票する。同じ失敗の open の Issue があれば起票しない | `未確定`（[要件](./要件.mark.md)。決める段: インターフェース定義設計）。workflow の `permissions` に `issues: write` を追加する |
| マージ前の上限の検査 | 作業 PR で実行する結合テスト（`build.test.ts`）が、NFR-1 の上限で `dist/` の配布ファイルのサイズを検査し、超えたら失敗する | 結合テストの一時フォルダのビルドの上限（`built-root.ts`）を NFR-1 に合わせるか、別のケースにするかはインターフェース定義設計で決める |
| キャッシュの削除 | commit して push した後、その commit で変わった配布ファイルごとに `https://purge.jsdelivr.net/gh/shuhei1101/mdmark@develop/{ファイル}` を呼ぶ。削除に失敗したら job を失敗にして失敗の通知に回す | 外部 API『jsDelivr』に purge のエンドポイントと上限を追加する |
| 単一 UC | 新規の単一 UC『developの配布物を再作成する』（`docs/scenario/SC-805-2.yaml`）に、再作成・手動の起動・失敗の起票・キャッシュの削除の失敗のシナリオを置く。『配布物をビルドして検査する』（SC-472-82）に、結合テストで上限の超過が分かるシナリオを追加する | - |
| 手動の起動 | `on` に `workflow_dispatch` を追加する | - |
| 代わりの経路 | GitHub Actions を実行できないときに、手元で `npm run build -- --develop` を実行して commit・push し、purge を呼ぶ手順を開発コマンドに追加する | - |
| lint | 変えた workflow を actionlint で検査する | - |
