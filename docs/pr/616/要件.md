# 要件

## 要望

| No | 機能 | 終わりの条件 |
| --- | --- | --- |
| 1 | 統合するかの決定 | ER 図の部品を map の ER 図へ統合して廃止するか、部品を残すかを、ユーザーの回答で決めて確認ログに残す。判断の材料に、ER 図の部品が持ち map の ER 図に写す先の無い値（テーブルの種類 `master`・`transaction` の札と色、テーブルの `color`、列の `nn`、題の行の範囲 `scope`・更新日 `updated`）と、外部で ER 図の部品を使用している dev-docs（dev-docs#59・#100。map への移行は dev-docs#201）を添える |
| 2 | 変換 | 統合する場合、文書の `<!-- er -->` の範囲の部品の定義（JSON）を、`<!-- map -->` の範囲（`erDiagram` の `mermaid` のブロック 1 つと補足 `<!-- map-data: {…} -->`）へ書き換える。テーブル・列（型・名前・PK・FK・説明）・関係（多重度・ラベル）を写し、テーブルの論理名 `label` は補足の `notes` のテーブルの説明の先頭へ、題 `title` は印の引数 `title` へ写す。畳んだテーブルは補足の `layout` の最初に閉じる指定へ写す。座標は写さずに自動配置に任せる。map に写す先の無い値は落として、文書・行・項目を変換の報告に挙げる。部品の定義を読めない範囲は書き換えずに、文書・行・理由を変換の報告に挙げる |
| 3 | 変換できる旨の警告 | 統合する場合、`er` の範囲は描かずに、map へ変換できる旨と変換の方法を書き方の警告で出す。点検（`mdmark check`）も同じ内容を通知する |
| 4 | 廃止 | 統合する場合、`er` の範囲を参照して描く処理・点検・部品・列の開閉の操作と、それを説明する設計書・使い方集・モック・ストーリー・テストを削除する |
| 5 | このリポジトリの図の書き換え | 統合する場合、使い方集・設計書の `er` の図を No 2 の変換で map の範囲へ書き換え、変換の報告に挙がった値を手で修正する |

統合する場合、変換は `migrations/next/` の移行の手順（`steps.yaml` の `op: call` と、文書を書き換えるスクリプト）にし、`mdmark upgrade` で適用する（#534 の `retired-diagrams` と同じ配置先）。

`未確定`: ER 図の部品を map の ER 図へ統合して廃止するか（決める段: 複合ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 統合して廃止する。`er` の範囲には変換できる旨の警告だけを出し、`破壊的変更` を付ける | 図の記載方法が map に統一され、ER 図を描く処理が 1 つになる | 使用する側は `mdmark upgrade` で書き換える必要があり、写す先の無い値は落ちる |
| B | 部品を残す。この作業 PR を取り下げ、計画の行を task-planner に取り下げてもらう | 使用する側の文書を変えずに済む | ER 図を描く処理が 2 つ残る |

推奨: A

flow・sequence と同じ進め方で移行の手順を用意でき、記載方法を map に統一できるため。
写す先の無い値は、複合ユースケース設計で一覧にしてユーザーへの確認に添える。
