# 要件

## 要望

`mdmark upgrade` が適用する前に取るコピー（`.mdmark/backup/{日時}/`）に、移行の手順が書き換える文書を全て入れ、手順の失敗か点検のずれでコピーから戻したとき、文書も適用する前の中身に戻す。

- 終了の条件: Issue の事象のフォルダ（`version: v0.10.0`、`build.out` の無い `build`（`include` だけ）の設定と、今の書き方のマーカーを持つ文書）へ `mdmark upgrade --yes` を実行すると、点検のずれで終了コード 1 になり、文書の中身が適用する前と同じで、コピーのフォルダに設定と文書が入っている
- 設定の `build` がスキーマに合わない場合も、索引の `docs[].path` が索引のフォルダの外の文書を指す場合も、`call` のスクリプトが書き換える文書をコピーの対象から落とさない
- 出したバージョン（`migrations/v0.10.0/`〜`migrations/v0.14.0/`）の移行の手順の配布物は書き換えない

`未確定`: コピーの対象の文書の集め方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `upgrade` の当て先の文書に、今の集め方（検めた後の設定の `build` と、索引のフォルダの下の Markdown）の文書へ追加して、`validateConfig` で検める前の設定の `build` の `include`・`exclude` と、索引の `docs[].path` の文書を集める（`call` のスクリプトと同じ集め方を追加する） | 出したバージョンのスクリプトを変えずに、スクリプトが書き換える文書とコピーの対象がそろう。修正する範囲が `upgrade.ts` に収まる | スクリプトと同じ集め方を CLI 側にも持つ |
| B | `call` の手順を適用する前後で、設定のフォルダの Markdown を全てコピーの対象にする | 集め方の食い違いが起きない | `build` の対象でない文書までコピーし、フォルダが大きいとコピーに時間がかかる |
| C | `validateConfig` がスキーマに合わない `build` を捨てずに残す | `upgrade` 側の集め方を変えずに済む | `mdmark check`・`build` など `validateConfig` を使用する全ての処理の振る舞いが変わる |

推奨: A

スクリプトは `--config` の設定を検めずに読み込んで文書を集めるため、CLI がコピーの対象を同じ規則で集めれば、出したバージョンの配布物を変えずに食い違いが解消する。
