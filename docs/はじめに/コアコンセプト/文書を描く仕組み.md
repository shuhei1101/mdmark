# 文書を描く仕組み

Markdown と設定を渡してから描かれるまでの流れと、テーマの層・機能のオン・オフの優先順

使う側のページが `mount` か `render` に Markdown と設定を渡してから、文書が描かれるまでの流れ。
見た目と機能が、何で決まるかを合わせて示す。

## 描かれるまでの流れ

1. 設定に既定を当てる。省いたキーは既定になり、型の合わない値は無視する
2. Markdown を解析し、GitHub Flavored Markdown の記法（表・タスクリスト・取り消し線・`www` の自動リンク）を HTML にする
3. 文書の [印](../../リファレンス/用語集.md) を拾う。`features` の印は機能のオン・オフに使い、対応表にある名前の印は印の場所に置き換え、それ以外の印は取り除く
4. 許可していない要素・属性・URL を落とす。`script` 要素・`on` で始まる属性・`style` 属性・`javascript:` の URL は残らず、スクリプトは実行されない。`href` と `src` は `http`・`https`・`mailto` と相対 URL だけ残る
5. `render` は、ここで本文の HTML 文字列を返す
6. `mount` は、要素の中に本文を描いて class `mdmark` を付け、印の場所があれば外部ライブラリのモジュールを読み、印刷の受け取りを付ける

## 機能のオン・オフの優先順

機能のオン・オフは、次の順に重ねて決まる。
後に挙げたものが、前に挙げたものを上書きする。

| 順 | 決めるもの | 書く場所 |
| --- | --- | --- |
| 1 | mdmark の既定 | [機能の既定](../../リファレンス/設定.md#機能の既定) |
| 2 | 設定の `features` | `opts.config.features` |
| 3 | 文書の印 | 文書の `<!-- features: +機能 -機能 -->` |

文書の印は、書いた順に重ねる。
同じ名前が何度も出たら、後に書いたものが勝つ。
知らない機能名と、`+`・`-` で始まらない引数は無視する。
`update` で本文を差し替えると、差し替えた本文の印で決め直す。

## テーマの層

mdmark の CSS は `@layer mdmark` に入る。
使う側が層の外に書いた CSS は、詳細度によらず mdmark の CSS に勝つ。
見た目は、次の 2 つで変えられる。

- `--mdmark-` で始まる CSS 変数の値を変える（一覧は [テーマの CSS 変数](../../リファレンス/API.md#テーマの-css-変数)）
- 層の外の CSS で、本文の規則を上書きする

使う側の `theme.css` は、使う側のページが `<link>` で層の外に読む。
mdmark は `theme.css` を読まない。
画面で OS の設定がダークのときは、色の変数がダークの値になる。
印刷では明るい配色に戻る。

## 外部ライブラリを読むタイミング

外部ライブラリのモジュールは、文書に対応表にある印があるときだけ、`import()` で読む。
印の無い文書では、外部ライブラリへの要求は 0 件になる。
同じ文書の同じ名前の印は、モジュールを 1 回だけ読む。
import map は使わない。

読み込みの間、印の場所には読み込み中の枠が出る。
モジュールを読めないとき、またはモジュールの `draw` が例外を投げたときは、その印の場所だけが知らせの枠に替わり、ほかの箇所は描かれる。
